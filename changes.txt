PART 2 - REVIEW OF THE FUNDAMENTAL LOGIC (rationale for the roadmap)
--------------------------------------------------------------------------------
VERDICT
- Data model (dayRecords: "YYYY-MM-DD" -> {status: logged|freeze|blocked}):
  sound and appropriately simple. Keep it.
- Efficiency: a non-issue at this scale (~3,600 entries for 10 yrs). Do NOT
  optimize. Any waste (recompute per render) is microseconds - cleanliness only.
- Architecture: one real weakness - freezes are DERIVED-BUT-STORED, kept in sync
  via two mutating useEffects. Symptoms: cascading renders (the
  set-state-in-effect lint errors), multi-pass settling, two sources of truth
  (freezeCount in meta vs {status:freeze} in dayRecords) that force undo to
  special-case the earn day, and rule changes not reconciling.
- FIX: make dayRecords (logged + blocked only) the SINGLE source of truth and
  compute streak + freezes as a pure function on render. This also makes cloud
  sync easy (sync the raw log, not derived state) and lets ONE engine be reused
  client-side and in the future server cron.

FRAMEWORK DECISION (from design chat)
- Next.js: REJECTED for this app. It is offline-first / anonymous-first, so SSR
  and server components buy little (anonymous data lives in localStorage the
  server can't see) while adding complexity; Supabase already provides the
  backend. Keep the Vite SPA; add a router for the routes we need.
- TypeScript + PWA + a real data/server-state layer: RECOMMENDED. These add
  capability the product actually needs and are where complexity is growing.
